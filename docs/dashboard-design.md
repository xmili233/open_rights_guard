# 设计方案讲解

> 本案例在 6 小时内完成调研、设计与部署。受时间和业务信息完整度限制，部分判断可能与真实市场需求存在偏差；如进入后续面试，可深度沟通讨论。

## 项目愿景

项目的愿景是：**让创作者和企业以极低的成本，最大化保障自己的合法权益。**

版权维护通常包含线索发现、证据固化、材料准备、案件提交和进度跟踪。用户真正需要做的不是重复操作，而是掌握进展，并在关键节点作出判断。

因此，产品的核心使用方式被定义为：

- **Agent 负责执行**：持续扫描、整理证据、准备材料并跟踪进度。
- **用户负责管理**：查看流程、核验结果并处理核心决策。
- **系统负责留痕**：关键文件、执行节点和状态变化均可回看。

## 为什么 MVP 只需要一个页面？

MVP 的目标不是覆盖完整版权业务，而是验证一条最小闭环：**用户能否快速了解全局，并在需要时进入具体案件。**

- 当前核心任务高度集中，暂时不需要多层导航。
- 单页可以减少页面跳转，让概览、趋势和案件形成连续的信息路径。
- 新能力只有在形成独立高频任务后，才有必要拆成新页面。

所以第一版采用单页仪表盘，而不是先搭建复杂的后台系统。

## 为什么把数据统计放在顶部？

基于我们的愿景，用户约 70% 的查看行为是在回答两个问题：**今天新发现了多少线索，昨天闭环了多少事项。**

因此，页面先展示维护作品、新发现、进行中案件、已处置事项、待核验线索和已固化证据，让用户进入页面后无需操作即可获得答案。

这些指标不是为了展示数据量，而是帮助用户快速判断：

- 今天是否出现异常增长；
- 当前是否存在积压；
- 哪一类事项最需要关注。

## 为什么案件详情使用流程节点？

案件是持续推进的长任务。用户进入详情后最先需要确认的是：**当前走到哪里、已经完成什么、下一步是什么。**

因此，详情页使用流程节点映射案件生命周期。已完成节点可以点击回看，当前节点突出显示，未进入的后续节点使用浅灰色显示。用户无需阅读执行日志，也能一眼分清已完成、当前和未开始的流程。

查看历史节点时，页面默认只展示该阶段的最终交付物，例如截图、视频、存证文件和法律文书，而不展示 Agent 对话与中间过程。

这同样来自项目愿景：尽可能减少 Agent 对用户的打扰。Agent 只是任务执行者，用户查看案件时真正关心的是可验证、可使用的交付结果。**只展示交付物可以减少无效信息，让用户更快完成判断。**

如果交付结果需要调整，用户可以点击“修改”开启下一轮处理。此时才显示当前案件上下文中的 Agent 对话，修改完成后生成新的交付物并回到对应流程节点。

## 为什么首页不提供 Agent，而只在案件修改中出现？

用户在仪表板首页主要完成两类任务：

- **查看统计数据**：了解新发现、已处置和正在推进的案件数量；
- **查找具体案件**：通过作品、主体或案件信息快速进入详情。

这两类任务都不需要通过聊天完成。统计需求可以通过仪表板迭代和用户配置持续满足，直接读取确定性数据更准确、更快速，也不会出现 Agent 语义理解错误和响应缓慢的问题。

案件查找则由右上角的统一搜索入口完成。搜索结合关键词模糊匹配与向量检索，提高自然语言查询的召回能力，并将用户直接带到匹配结果，无需先与 Agent 多轮沟通。

**长期在首页显示聊天入口会增加视觉噪声，也会让产品退化成一个通用聊天工具。**

Agent 只在案件材料不足或需要修改时出现。此时上下文被限定在当前案件，用户可以对照已有文件说明要求，由 Agent 完成补充、替换和重新整理，再将结果回到原流程中。

## Agent 如何设计？

Agent 的主要任务是从不同渠道收集某项作品的侵权信息。需要交付的材料类型通常是固定的，主要不确定性是部分材料可能无法获取。因此，最适合的执行形态是 **Workflow，而不是完全自主的 Agent**。

整体 Workflow 分为两层：案件进度 Workflow 负责调度与状态，任务 Workflow 负责完成某一次具体交付。

### 第一层：案件进度 Workflow

案件进度 Workflow 管理案件从发现到结案的整体状态。它包含两类上下文：

- **企业共享信息**：企业身份、授权信息、作品权属材料、作品库和用户权限。这些信息由同一企业下的多个案件实例共用。
- **当前案件信息**：案件编号、目标作品、侵权主体、来源渠道、原始链接、当前节点、已有交付物、缺失材料和时间要求。

这一层只负责创建任务、接收结果、更新流程节点，以及在材料缺失时触发重试或人工判断，不直接执行截图、录屏等操作。

### 第二层：任务执行 Workflow

任务 Workflow 只负责一个明确任务，例如在某个渠道完成证据固化。它只需要当前任务相关的上下文：

- 当前负责的渠道及目标链接；
- 需要交付的证据清单；
- 文件格式、完成条件、重试次数和失败处理规则。

证据清单由平台开发人员预先定义，例如侵权页面完整截图、商品或内容信息、销量与传播数据、主体信息、带时间和来源链接的页面记录，以及必要的操作录屏。Agent 不是“看看能找到什么”，而是按清单逐项交付；无法取得的材料必须返回明确的缺失项和原因。

### 渠道能力如何拆分？

- **MVP 阶段**：使用一个任务 Agent，并为不同渠道配置独立 Skill。执行某个渠道时只加载对应 Skill，减少无关上下文，方案也更简单。
- **需要规模化时**：为每个渠道设置独立任务 Agent。不同渠道可以并发执行，平台规则互不干扰，单个渠道失败也不会阻塞其他任务。

### 为什么把截图和录屏交给 Tools？

Agent 只负责判断何时调用工具，Tools 负责真正完成截图、录屏、元数据写入和文件保存。工具输出使用固定格式，并在失败时返回可重试的错误。

这样可以把跨平台操作、格式校验和重试逻辑固定在代码中，不需要让 Agent 学会每个平台的截图与录屏细节，进一步降低对模型能力的要求、运行成本和不确定性。

### 为什么不把执行过程传回案件 Workflow？

任务 Workflow 完成后，只向案件进度 Workflow 返回结构化结果：执行状态、交付文件、缺失材料、失败原因，以及是否需要人工处理。

详细操作过程可以单独留存用于审计，但不进入上层 Agent 的上下文。这样可以避免无效信息持续膨胀，减少 Token 消耗，也降低历史执行细节干扰后续判断的风险。

**案件 Workflow 管进度，任务 Workflow 管交付，Tools 管确定性执行；上下层只传结构化结果。**
