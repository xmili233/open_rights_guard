# 设计方案讲解

> 本案例在 6 小时内完成调研、设计与部署。受时间和业务信息完整度限制，部分判断可能与真实市场需求存在偏差；如进入后续面试，将结合反馈持续迭代。

## 项目愿景

项目的愿景是：**让创作者和企业以极低的成本，最大化保障自己的合法权益。**

版权维护通常包含线索发现、证据固化、材料准备、案件提交和进度跟踪。用户真正需要做的不是重复操作，而是掌握进展，并在关键节点作出判断。

因此，产品的核心使用方式被定义为：

- **Agent 负责执行**：持续扫描、整理证据、准备材料并跟踪进度。
- **用户负责管理**：查看流程、核验结果并处理核心决策。
- **系统负责留痕**：关键文件、执行节点和状态变化均可回看。

## 02 为什么 MVP 只需要一个页面？

MVP 的目标不是覆盖完整版权业务，而是验证一条最小闭环：**用户能否快速了解全局，并在需要时进入具体案件。**

- 当前核心任务高度集中，暂时不需要多层导航。
- 单页可以减少页面跳转，让概览、趋势和案件形成连续的信息路径。
- 新能力只有在形成独立高频任务后，才有必要拆成新页面。

所以第一版采用单页仪表盘，而不是先搭建复杂的后台系统。

## 03 为什么把数据统计放在顶部？

基于当前场景假设，用户约 70% 的查看行为是在回答两个问题：**今天新发现了多少线索，昨天闭环了多少事项。**

因此，页面先展示维护作品、新发现、进行中案件、已处置事项、待核验线索和已固化证据，让用户进入页面后无需操作即可获得答案。

这些指标不是为了展示数据量，而是帮助用户快速判断：

- 今天是否出现异常增长；
- 当前是否存在积压；
- 哪一类事项最需要关注。

## 04 为什么紧接着展示趋势与案件状态？

单日数字只能说明结果，趋势才能帮助用户判断变化是否持续。

- **近七天趋势**用于识别线索增长、处置速度和二者之间的差距。
- **案件状态**用于判断事项主要停留在哪个流程阶段。
- **维护项目分布**用于识别哪些作品正在产生更多风险。

信息顺序遵循“先看结果，再看原因，最后进入明细”，避免用户在多个模块之间反复查找。

## 05 为什么用案件列表承接具体进展？

当用户发现异常后，下一步通常是查看某个案件，而不是继续阅读更多图表。

案件列表只保留编号、侵权主体、请求金额、最新进度和详情入口。点击详情后使用大尺寸弹窗展示完整内容，既保留仪表盘上下文，也为材料和流程提供足够空间。

每页展示 20 条，满足集中查看需要，同时避免一次加载过多信息。

## 06 为什么案件详情按流程组织？

版权案件是一个有明确阶段的长任务。相比展示 Agent 的执行日志，用户更关心：**现在走到哪里、已经产出了什么、接下来等待什么。**

详情页按以下节点组织：

1. 证据固化
2. 起诉材料
3. 立案受理
4. 审理裁判
5. 执行结案

已完成节点可以点击回看，节点下直接展示截图、视频、存证文件、起诉材料和法院文书。文件本身就是结果，因此不再增加二级详情框或重复的“查看”按钮。

## 07 为什么 Agent 只在需要修改时出现？

大多数时候，用户只需要查看系统已经完成的结果。长期显示聊天入口会增加视觉噪声，也会让产品退化成一个通用聊天工具。

因此，Agent 只在用户认为材料不足或需要调整时出现：

- 右侧保留当前材料，方便对照；
- 左侧打开对话，用户用自然语言说明修改要求；
- Agent 处理补充、替换和重新整理，结果仍回到原流程中。

这种设计让对话服务于任务，而不是让用户围绕对话完成任务。

## 08 为什么采用“Agent 执行，用户决策”？

版权维护包含大量重复工作，但材料提交、诉讼请求和关键法律动作具有较高失败成本。

因此 MVP 采用受控 Agent：

- 路径明确的工作由固定流程执行，保证可审计、可重试；
- 需要理解非结构化材料时由 Agent 辅助判断；
- 关键文件可以回看，重要动作需要用户确认；
- Agent 失败时停止在当前节点，不虚构已完成结果。

这套分工同时降低操作成本，并保留用户对核心权益决策的控制权。

## 09 当前版本验证什么？

本版本优先验证三件事：

- 用户能否在进入页面后快速理解当前状态；
- 用户能否从异常指标顺利找到具体案件；
- 用户能否看懂案件进展，并在材料有问题时发起修改。

后续迭代将基于真实用户反馈，补充指标口径、角色权限、异常提醒和关键决策节点，而不是预先堆叠功能。
